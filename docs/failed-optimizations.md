# 効果がなかった速度改善の記録

速度改善を試して効果がなかった、または逆効果だった手の記録。
同じ手への再挑戦を防ぐため、速度改善に着手する前にここを確認すること。
新たに効果がなかった手はこのファイルに追記すること (CODEBASE.md を参照)。

計測はいずれも Apple Silicon (arm64) の release ビルドで、
criterion のベンチ (`benches/benches/codec.rs`) または
単体のマイクロベンチによる。

## 採用しなかった手

### folded 中間 Vec の廃止 (2026-07-04)

- 試した手: Rice 統計の収集で folded 残差の中間 Vec をやめ、走査のたびに fold を再計算する
- 期待: 中間バッファの確保と書き込みの削減
- 実測: encode +3-6% の悪化
- 原因: fold の再計算は L1 ヒットのロードより高くつく

### read_rice のリーダー状態をローカルへ引き上げるバッチ読み (2026-07-04)

- 試した手: Rice 残差のデコードでビットリーダーの状態をローカル変数に引き上げてまとめて読む
- 期待: 状態の store / load の削減
- 実測: decode_tonal +7.6% の悪化
- 原因: 低速パス (リフィル) との切り替えで状態の往復が増える

### fixed::best_order の階差列 Vec 化 (2026-07-04)

- 試した手: 次数選択の階差列を windows + collect で Vec に組み立てる
- 期待: 自動ベクトル化しやすい形への変換
- 実測: 持ち回りカスケード 1 パスに負ける
- 原因: 中間 Vec の確保と書き込みが直列依存の除去分を上回る

### 自己相関のラググループ 2 (2026-07-04)

- 試した手: 自己相関のラグ同時処理数を 2 に変更する
- 期待: レジスタ圧の低減
- 実測: ラググループ 8-9 が最速 (4 も可)
- 原因: ロード共有の利得がラグ数に比例して効く

### LPC 残差の windows().map() + extend での i32 化 (2026-07-04)

- 試した手: サンプル格納を i32 にした残差計算を `windows(ORDER + 1).map()` を `extend` する形のまま書く
- 期待: i32×i32→i64 の widening 乗算 (smlal) による自動ベクトル化
- 実測: smlal は生成されるが実効はスカラー並み (単体 +5% 程度)
- 原因: 隣接ウィンドウのペア化にシャッフル (ext / dup) が挟まる
- 対処: 「出力 4 点ブロック + 係数スプラット + スカラーアキュムレータ 4 本 + resize 済みスライスへの直接書き込み」の形にすると単体 3.3 倍 (採用済み)

### Rice 統計の u32 格納 + u64 widening 和 (2026-07-04)

- 試した手: folded 残差を u32 で格納し、シフト和の加算だけ u64 へ widening する
- 期待: ロード幅半減によるスループット向上
- 実測: +20% の悪化
- 原因: u32→u64 の拡張命令がレーン利得を食い潰す。現行の「u64 格納 + 8 本同時シフト和」が最適だった

### Rice 統計の u32 飽和和 (2026-07-04)

- 試した手: シフト和を u32 の飽和加算 (NEON uqadd 狙い) で閉じる。飽和した sums はエスケープ符号に必ず負けるため選択結果は不変という証明付き
- 期待: u32 4 レーンで閉じた集計
- 実測: 2.6 倍の悪化
- 原因: LLVM が `saturating_add` のループをベクトル化しない (uqadd はごく一部にしか出ない)

### 自己相関の f32 積和 (2026-07-04)

- 試した手: 窓適用済みサンプルを f32 で格納し、積和も f32 (f32x4 で f64x2 の 2 倍幅) で計算する
- 期待: 自己相関の 2 倍速
- 実測: 自己相関単体 26% 改善、encode -1.7%。ただし tonal (純正弦波和音) で圧縮率 +3.9% の悪化
- 原因: f32 積和の蓄積誤差 (相対 1.4e-7) が高予測ゲイン信号の Levinson-Durbin で増幅され、係数品質が落ちる。リファレンス実装 libFLAC が f32 で安全なのは、格納だけ f32 で積和は f64 だから

### 自己相関の f32 格納 + f64 積和 (2026-07-04)

- 試した手: リファレンス実装 libFLAC と同じ型構成 (f32 格納、f64 積和)
- 期待: ロード幅半減 + f64 精度の維持
- 実測: 1.6 倍の悪化
- 原因: f32→f64 の拡張 (fcvtl) がループ内に挟まり、レーン利得を食い潰す

### 自己相関の f32 積和 + 64 サンプルごとの f64 2 段和 (2026-07-04)

- 試した手: f32 積和の蓄積誤差を抑えるため、64 サンプルごとに f32 部分和を f64 へ流す
- 期待: 精度と速度の両立
- 実測: 精度は相対 2.9e-9 まで回復するが、速度は f64 直接比 +5% しか残らない
- 原因: ブロック境界の変換 (ラグ 9 本 x 8 レーン) が f32 の利得を食う。出力が変わる代償に見合わないため不採用

### Rice 統計の core::simd (nightly) による明示的な u32 飽和和 (2026-07-04)

- 試した手: nightly の `core::simd` で `Simd<u32, 4>` の `saturating_add` を明示的に書き、LLVM の自動ベクトル化に頼らず uqadd を出す
- 期待: 自動ベクトル化が乗らなかった u32 飽和和 (前項) をレーン幅 2 倍で実現する
- 実測: 現行の u64 8 本同時とほぼ互角 (差 2-3%)
- 原因: 飽和加算はスループットが通常の加算より低く、レーン幅の利得を相殺する。「u64 格納 + 8 本同時シフト和」が命令スループット上も最適だった
- 補足: nightly 化はライブラリ利用者にも nightly を強制するため、互角の性能では採用理由にならない

## 共通の罠

再挑戦する場合や新しい手を試す場合は、以下の罠を先に確認すること。

- ループ内の widening (u32→u64、f32→f64) は LLVM で一貫して負ける。widening が勝つのは乗算自体が widening 命令になる場合 (smull / smlal、vpmuldq) だけ
- ループ内の `push` / `extend_from_slice` は容量チェックがブロック全体の自動ベクトル化を殺す。事前に長さを確定した resize 済みスライスへ直接書き込むこと
- `vec![0; n]` はゼロページを返す calloc 経路になり、32 KB 級では書き込み時のページフォルトが計算本体の 2 倍のコストになる。`Vec::with_capacity` + `resize` は malloc + memset で軽い
- マイクロベンチのループ内で Vec を生成すると malloc / free が計測を支配し、比較が無意味になる。出力バッファは外で確保して渡すこと
- 変更前後の比較は必ずエンコード出力のバイト列一致で検証すること。一致しない変更 (浮動小数点の精度が変わる等) は圧縮率の再測定が必要で、tonal のような高予測ゲイン信号を必ず含めること
